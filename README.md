# SALAH Governance — owner-controlled trust root

This repository is separate from the SALAH application candidate. Its Git history and owner-controlled access, not a SALAH workspace file or a self-reported digest, are the trust assumption. The named final approver is **SH Tech**, the sole project owner. No separate independent security reviewer exists. Owner approval and independent security review are distinct; a sole-owner decision must explicitly acknowledge the risk of proceeding without the latter. No record in this repository is a signature or a claim of independent review.

The original four `G1_SOURCE_VERIFIER_PIN` records are preserved in `governance/approvals.jsonl`. They pin the existing source-verification CLI, not H171 source bytes or notification runtime behavior. The owner-governance transition at register revision 5 binds the 12 October 2026 H171 candidate packet SHA-256, exact candidate path/hunk-ID scope, the previous governance commit and file hashes, and the revised policy/bootstrap/test hashes. Its state is `CANDIDATE_SCOPE_APPROVED`, with `admissionStatus: NOT_ADMITTED`. It does **not** admit whole files, approve final generated-bundle bytes, activate C14, certify Gate A/B, or grant runtime/production authority.

The separate version-1 `OWNER_RISK_VERIFIER_PIN` mechanism is for a future successor source verifier. It does not reinterpret the historical G1 security-review field. A successor requires append-only DRAFT → FINAL_BYTES_APPROVED → ACTIVE decisions binding the exact new verifier SHA-256, mapping and three controlled-only hashes, policy/bootstrap revisions, the reviewed H171 packet hash and finite source/test scope, the historical G1 active decision it supersedes, and SH Tech's explicit acceptance of proceeding without independent security review. The `--owner-risk-candidate` check requires the packet-bound governance transition to be clean and committed before it can execute the candidate verifier. A dirty checkout, absent packet, changed verifier, malformed/conflicting record, or absent exact final-byte owner decision fails closed. No successor pin record or final successor verifier SHA has been supplied or activated in the current register; the existing G1 pin remains historical authority for its original bytes only.

The append-only `OWNER_GOVERNANCE_V2_CORRECTION` schema version 1 repairs the uncommitted V2 candidate without editing its row. It must immediately follow exactly one V2 row. Its predecessor decision ID and SHA-256 bind the exact canonical V2 JSON line including its terminating LF; its `priorRegisterPrefixSha256` binds every register byte through that predecessor, also including the final LF. V1 and V2 each bind the register prefix immediately before their own row, not one another's prefix. The correction pins final canonical policy, bootstrap and test-file SHA-256 values, the unchanged H171 packet and finite scope, and SH Tech's explicit risk acceptance. Its sole state is `PROPOSED_CORRECTION`: the record is evidence, not authority, source admission or verifier activation. Missing, reordered, duplicated, altered or conflicting correction records fail validation. The committed G0 bootstrap predates this schema and cannot approve its own replacement; only a later explicit SH Tech review of exact final governance bytes and an owner-controlled commit can establish the proposed trust transition. Until then, the working-tree check must remain pending/non-authoritative. A subsequent exact successor verifier pin remains a separate approval decision.

The owner-admission schema and `verifyFiniteHunkProjection` reject extra, missing, altered, overlapping, duplicated, and reordered approved spans. A future final-byte decision must carry exact old/new bytes and hashes for every approved source/test sub-hunk, a pinned transitive generation input tree and generator, and an independently reviewed generated-output diff. A successful projection is only byte-level diagnostic evidence; it is not AlarmManager registration, device delivery, or release certification. The historical SALAH protected hashes remain audit history and are not replaced by current workspace hashes.

Run `node --test tests/bootstrap-trust.test.mjs` for governance tests. `node bootstrap/verify.mjs` remains diagnostic. `node bootstrap/verify.mjs --owner-transition /absolute/path/to/reviewed-packet.md` additionally checks the packet and transition hashes. Until the revised governance files and appended decision are committed by the owner, that command reports a pending transition and exits nonzero. No tool should treat an uncommitted governance checkout as an active trust root. The existing `--g1-candidate` path still requires a clean, committed governance checkout and exact verifier bytes before source-only execution.

G2 mandatory entrypoint protection and G3 amendment execution remain pending. No SALAH application file, verifier, notification bundle, Android/iOS build, or device state is changed by this governance transition. Commit/push, protected-source admission, and any final verifier pin require separate owner action and evidence.
